# Disaster recovery plan

How this application recovers from failures: what is protected today, how to recover from each kind of incident, and what production would add.

**Short version:** the infrastructure can be rebuilt from Terraform in about 20 minutes, the database can be restored to any point in the last 7 days, and a bad release is rolled back automatically. The main gaps (single zone, single region, state versioning off) are deliberate cost choices for dev and are listed at the end with their fixes.

---

## 1. Recovery targets

**RTO** = how long until the service is back. **RPO** = how much data can be lost.

| Failure | Dev today: RTO | Dev today: RPO | Production target |
|---|---|---|---|
| Bad release | ~1 min (automatic rollback) | none | same |
| Container or instance crash | seconds (Cloud Run replaces it) | none | same |
| Data deleted or corrupted | ~30-60 min | to the second, within 7 days | same |
| Zone outage | Cloud Run: none. Database: until the zone returns | none | minutes (HA failover), RPO 0 |
| Region outage | hours (rebuild in another region) | up to 24 h (last backup) | < 1 h (promote replica), RPO minutes |
| Whole environment lost | ~20-30 min (Terraform) | up to 24 h | same, with cross-region backups |

---

## 2. What protects the system today

| Component | Protection | Where it's set |
|---|---|---|
| **Cloud SQL data** | Automated daily backups at 02:00 UTC, 7 kept. Binary logs enable **point-in-time recovery** for 7 days | `terraform/modules/cloudsql` |
| **Infrastructure** | Everything is Terraform; remote state in GCS with locking | `terraform/` |
| **Application image** | Immutable tags in Artifact Registry; last 10 images always kept for rollback | `terraform/modules/artifact-registry` |
| **Running versions** | Every release is a named Cloud Run revision; traffic can move back instantly | Cloud Run |
| **Bad deploys** | Pipeline smoke-tests through the load balancer and rolls back automatically | `.github/workflows/release.yml` |
| **Static files** | Source of truth is Git; bucket keeps deleted files for 7 days (soft delete) | `terraform/modules/storage` |
| **DB password** | Secret Manager (versioned); regenerated by Terraform if needed | `terraform/modules/cloudsql` |
| **Compute** | Cloud Run is regional: it survives the loss of a single zone | Cloud Run |

## 3. Runbooks

Each runbook is written to be followed under pressure. Set these first:

```bash
PROJECT=php-cloudrun-platform; REGION=europe-west1
INSTANCE=$(gcloud sql instances list --format='value(name)' --filter='name~php-app-dev')
```

### 3.1 A release is broken

The pipeline rolls back automatically if the smoke test fails. If a problem shows up later:

```bash
gcloud run revisions list --service php-app-dev --region $REGION        # find the last good revision
gcloud run services update-traffic php-app-dev --region $REGION \
  --to-revisions php-app-dev-dev-v1-0-9=100                             # move all traffic back
```

Then fix forward with a new tag. (The next release sends traffic to the latest revision again automatically.)

### 3.2 Data was deleted or corrupted

Restore a copy **next to** the live database first, check it, then switch. Never overwrite the only copy.

```bash
# 1. Clone the database to just before the incident (point-in-time recovery)
gcloud sql instances clone $INSTANCE ${INSTANCE}-restore \
  --point-in-time '2026-11-17T10:15:00Z'

# 2. Check the data in the clone (e.g. via Cloud SQL Studio in the console)

# 3. Copy the good data back: export from the clone, import into the live instance.
#    Use a bucket the instances' Cloud SQL service accounts can write/read
#    (shown by: gcloud sql instances describe <name> --format='value(serviceAccountEmailAddress)')
gcloud sql export sql ${INSTANCE}-restore gs://$PROJECT-dr-exports/app.sql --database app
gcloud sql import sql $INSTANCE gs://$PROJECT-dr-exports/app.sql --database app

# 4. Delete the clone when finished
gcloud sql instances delete ${INSTANCE}-restore
```

For a full restore from a nightly backup instead: `gcloud sql backups list --instance $INSTANCE`, then `gcloud sql backups restore <BACKUP_ID> --restore-instance $INSTANCE` (this overwrites the instance).

### 3.3 The database instance was deleted

In dev, deletion protection is off and automated backups are removed with the instance, so the data would be lost. Recovery is a rebuild (3.6) with an empty database. **In production this must not be possible:** deletion protection on, plus retained/exported backups (see section 5).

### 3.4 A zone fails

- **Cloud Run** keeps serving from other zones automatically.
- **Cloud SQL** is single-zone in dev (`ZONAL`), so the database is unavailable until the zone recovers. `/readyz` reports `503` and the status page shows "Database unreachable"; the app itself stays up.
- **Production fix:** `db_availability_type = "REGIONAL"` gives a standby in another zone with automatic failover.

### 3.5 The whole region (europe-west1) fails

1. Set `region = "europe-west4"` (or another region) in `terraform/envs/dev/terraform.tfvars`.
2. `terraform apply`. This creates a new database, Cloud Run service and load balancer backend in the new region. The load balancer is global, so its IP address can stay the same in production.
3. Restore data: from a cross-region export (production) or start empty (dev today).
4. Release the current tag again so the image is deployed to the new region.

### 3.6 Rebuild everything from scratch

The order matters because later steps depend on earlier ones:

| Step | Command | Time |
|---|---|---|
| 1. Foundation (APIs, state bucket, CI identities) | `terraform -chdir=terraform/bootstrap apply` | ~3 min |
| 2. Environment | `terraform -chdir=terraform/envs/dev apply` | ~15 min (Cloud SQL) |
| 3. GitHub settings | Update `APP_URL` with the new load balancer IP | 1 min |
| 4. Application | Push a release tag | ~5 min |
| 5. Data | Restore from backup/export if available (3.2) | varies |

### 3.7 Terraform state is lost or damaged

This happened during the build (network drop mid-apply) and was recovered without losing anything:

1. A stuck lock: `terraform force-unlock <LOCK_ID>`
2. Terraform saved its progress locally: `terraform state push errored.tfstate`
3. Resources created but not recorded: `terraform import <address> <id>`
4. Check with `terraform plan`: it should show nothing to destroy or replace.

If the state file itself were deleted, every resource can be re-imported the same way. **Enabling state versioning** (one variable) would make this a simple "restore the previous version".

### 3.8 The database password is exposed

```bash
cd terraform/envs/dev
terraform apply -replace=module.cloudsql.random_password.db
```

This generates a new password, updates the MySQL user and adds a new Secret Manager version. Then release again (or redeploy the current image) so new Cloud Run instances read the new password.

### 3.9 The CI/CD pipeline is compromised or GitHub is down

- **Cut access instantly:** disable the GitHub identity provider. No keys exist, so nothing else needs rotating:
  ```bash
  gcloud iam workload-identity-pools providers update-oidc github-oidc \
    --workload-identity-pool github --location global --disabled
  ```
- **Deploy without GitHub (break-glass):** an admin can build and deploy from their own machine:
  ```bash
  gcloud builds submit --config cloudbuild.yaml --region $REGION \
    --substitutions _IMAGE=$REGION-docker.pkg.dev/$PROJECT/php-app/php-app,_TAG=hotfix-1,_REPORTS_BUCKET=$PROJECT-build-reports
  gcloud run deploy php-app-dev --region $REGION \
    --image $REGION-docker.pkg.dev/$PROJECT/php-app/php-app:hotfix-1
  ```

### 3.10 The project is deleted

A deleted project can be restored for 30 days: `gcloud projects undelete php-cloudrun-platform`. After that, rebuild in a new project (3.6) with a new project ID.

## 4. Testing the plan

A recovery plan that has never been run is a guess. Recommended routine:

| How often | Test |
|---|---|
| Every release | Automatic: smoke test + rollback (already proven during this build) |
| Monthly | Restore a point-in-time clone (3.2) and check the visit counter table |
| Quarterly | Full rebuild in a scratch project (3.6) and time it against the RTO |

## 5. Gaps today and the production fix

| Gap in dev | Risk | Production fix |
|---|---|---|
| Cloud SQL `ZONAL` | Database down during a zone outage | `REGIONAL` (HA with automatic failover) |
| One region, no replica | Long recovery from a region outage | Cross-region read replica, promoted on failover |
| Backups stored in the same region and deleted with the instance | Instance deletion or region loss loses data | Deletion protection on; retain backups after deletion; nightly `gcloud sql export` to a dual-region bucket |
| State versioning off | No easy rollback of a damaged state file | `enable_state_versioning = true` |
| Artifact Registry deletes images older than 30 days (keeps the newest 10) | Cannot roll back further than that | Longer retention for prod tags (`v*`) |
| Single project for everything | One mistake can affect all environments | Separate projects for dev and prod |
